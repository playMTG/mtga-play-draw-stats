## 高优先级（影响数据正确性或可运维性）

### H1. 监听线程因日志权限异常崩溃且不再恢复

- 位置：`app/main.py`（`_watch_loop` 内身份探测处）、`app/backfill.py`（`collect_sources`）
- 现象：Windows 上 MTGA 独占 `Player.log` 时，`Path.exists()` 可能抛 `PermissionError`。身份探测处的列表推导未捕获该异常，`_watch_loop` 线程直接结束。
- 已有实证：`data/panel-r5.err.log` 出现 `PermissionError: [WinError 5] 拒绝访问。: '...\Player.log'`。
- 连带影响：
  - `_state["watching"]` 仍为 `True`，页面显示「监听中」，实际新对局不再入库。
  - `collect_sources()` 同样对 `p.exists()` 无保护；启动回填被外层 `except Exception: pass` 吞掉后会静默失败。
- 建议方向：所有对日志路径的 `exists/stat/open` 统一容错；监听线程崩溃时置错误状态并自动重启；回填失败写入可见状态。

### H2. 迟到的 `finalMatchResult` 可能盖到错误对局

- 位置：`app/events.py`（`_on_final_result`）
- 现象：优先写 `_cur`，为空则写 `_last`，**不校验结果中的 matchId**。注释已承认 Brawl 下结果会晚于 `MatchCompleted`；若下一局已进入 `Playing`，上一场的胜负会写入当前对局。
- 影响：入库按 `match_id` 幂等，错误结果会固定下来，胜率与先后手关联均被污染。
- 建议方向：按结果载荷中的 matchId 对齐目标；对不上则不写入，或写入独立待确认队列。

### H3. 监听写库「毒数据」会堵死整条流水线

- 位置：`app/main.py`（`_watch_loop.flush`）
- 现象：`flush()` 无按条容错。某条记录在 `upsert_match` / `insert_rank` 持续抛错时，`pending_*` 不清空，其后每轮原地重试，后续对局永远无法提交。
- 影响：监听表面正常，新对局静默丢失；状态仅有 `last_error=ExceptionName`。
- 建议方向：按条 try/except；单条失败丢弃并记日志，队列继续前进。

### H4. `stop.bat` 端口匹配过宽，可能误杀无关进程

- 位置：`stop.bat`
- 现象：`findstr :8765` 为子串匹配，会命中 `:18765`、`:87650`、`:28765` 等，再 `taskkill` 对应 PID。
- 建议方向：精确匹配本地端口 8765（解析 netstat 本地地址列，或 `Get-NetTCPConnection -LocalPort 8765`）。

## 中优先级（功能失效、并发或体验问题）

### M1. BO3 局号在未见到 turn>1 时可能不推进

- 位置：`app/events.py`（`_on_gre` 中 `_game_idx` / `_saw_turn_gt1`）
- 现象：局号推进依赖「先见到 turn>1，再见到 turn=1」。投降/秒退未进入 turn 2 时，下一局仍复用 `game_no=1`。
- 影响：调度次数与逐局先后手可能串到错误的 game_no。
- 建议方向：用明确的对局开始/结束事件或 gameNumber 字段推进局号，不单靠 turn 边沿。

### M2. `config.json` 损坏时静默回退默认值

- 位置：`app/config.py`（`load_config`）
- 现象：`JSONDecodeError` / `OSError` 被吞掉，直接用内置默认。
- 影响：自定义 `my_player_id`、`db_path`、日志路径「消失」，表现为丢历史或身份解析失败，且无提示。
- 建议方向：损坏时写 stderr/状态字段；必要时拒绝启动或标记「配置未加载」。

### M3. 连续战绩维度永远无法「样本足够」

- 位置：`app/insights.py`（`dims['streak']` 与 `_dimension`）
- 现象：`_dimension(..., min_n)` 未传 `p`，`enough = n >= min_n and p is not None` 恒假。
- 影响：被针对指数中的连续战绩始终显示「资料不足」，功能实际失效（并非只是小样本问题）。
- 建议方向：要么补上可用的 p 值/描述性结论，要么在 UI 明确改为纯记录项并去掉「不够」话术。

### M4. 前端多接口缺少请求序号防竞态

- 位置：`web/app.js`（`loadMatches` / `loadCommanders` / `loadTargeting` / `loadOverview` 等）
- 现象：`loadDeckDetail` / `loadDaily` 已用 request token；其余接口未对等处理。叠加定时 `reload()` 后，切换筛选时可能出现旧范围响应覆盖新范围。
- 建议方向：统一带请求序号（或 AbortController），过期响应直接丢弃。

### M5. 卡名同步线程绕开 `_db_lock`

- 位置：`app/main.py`（`_cards_sync_loop`）、`app/cards_sync.py`
- 现象：`card_sync_enabled` 打开时，同步线程自建 SQLite 连接读 stats、写 cards，不走全局锁，与监听/API 并发。
- 影响：可能触发 `database is locked`；异常被 `except Exception: pass` 吞掉。
- 建议方向：与主连接共用锁，或明确单写者队列。

### M6. 启动回填使用第二连接写库，与 API 并发

- 位置：`app/main.py`（`_boot_tasks` → `app/backfill.backfill` → `store.connect`）
- 现象：回填自开连接，API 走 `get_conn()+_db_lock`。启动期间双写者，依赖 `busy_timeout=15s` 硬扛。
- 影响：长事务可能超时中断整文件回填循环。
- 建议方向：回填也走同一连接/锁，或启动期间暂停 API 写路径并明确状态。

### M7. 关闭时未与监听线程同步

- 位置：`app/main.py`（`on_shutdown`）
- 现象：直接 `_conn.close()`，不 join 监听线程、不取 `_db_lock`。
- 影响：正在 `flush()` 的写入可能异常；若同时命中 H3，pending 状态更难恢复。
- 建议方向：停止监听标志 → 等待线程退出 → 再关连接。

### M8. `my_deck_tag` 空字符串会挡住后续套牌名

- 位置：`app/store.py`（`upsert_match` 中 `COALESCE(matches.my_deck_tag, excluded.my_deck_tag)`）
- 现象：`COALESCE` 把 `''` 当作已设置。
- 影响：一旦写入空字符串，后续日志/导入的套牌名无法覆盖。
- 建议方向：用 `NULLIF(..., '')`，或入库前把空串规范为 NULL。

### M9. CSV 导出未防护 Excel 公式注入

- 位置：`app/stats.py`（`export_rows`）
- 现象：`opponent_name` 等字段原样写入 CSV。
- 影响：对手名若以 `=`、`+`、`-`、`@` 开头，Excel 可能当公式执行。
- 建议方向：导出时对危险前缀加前导 `'` 或剥离。

### M10. 身份探测可能认错人

- 位置：`app/backfill.py`（`detect_player_id`）
- 现象：对全部文件统计 `reservedPlayers` 中 `userId` 频次，取最高频者。
- 影响：若日志大量来自同一好友/切磋对象，可能锁定错误身份；座位、先后手、胜负全部错位或置空，并被监听继承。
- 建议方向：结合 config 的 `my_player_id`；探测结果写入可核对的状态/设置项，不静默定案。

### M11. 日志轮换丢弃未闭合多行块

- 位置：`app/watcher.py`（轮换分支直接 `self._asm = RecordAssembler()`）
- 现象：注释写「先把组装器里未闭合的块兜底产出」，代码未调用 `flush()`；`_flush_asm` 定义了但未使用。
- 影响：跨轮换截断的 JSON 块可能丢失（与 H2/H3 叠加时更难排查）。
- 建议方向：轮换前 flush 旧 assembler；与 backfill 的 `iter_records` 尾部 flush 语义对齐。

## 低优先级 / 卫生

### L1. FastAPI 废弃启动钩子

- 位置：`app/main.py`（`@app.on_event("startup"/"shutdown")`）
- 现象：DeprecationWarning 持续出现在测试与 `data/panel*.err.log`。
- 建议：迁移到 `lifespan`。

### L2. 仓库/工作区杂物

- 根目录存在误生成的 `NVIDIA Corporation/umdlogs`。
- `data/` 内堆积大量 `test-r*`、probe DB、panel 日志（已被 gitignore，但干扰本地排查）。
- 建议：删除误生成目录；开发临时库/日志约定独立子目录并定期清理。

### L3. 面板错误日志编码损坏

- 位置：`data/panel.err.log` 等
- 现象：路径中文显示为 `MTGA鍏堝悗鎵嬫彃`（代码页/pythonw 环境问题）。
- 建议：统一 UTF-8 日志写入方式。

### L4. 前端转义不完整（低风险）

- `archTag` 对未知 archetype 未 `esc()`。
- `archSelect` 的 inline `onchange` 仅转义反斜杠与单引号；当前 key 多为 `grpId:数字`，实际风险低。
- 建议：统一走事件绑定 + `dataset`，避免拼 inline handler。

### L5. 默认 Bot 套牌匹配过宽

- 位置：`app/config.py` / `config.example.json`（`bot_deck_patterns: ["bot"]`）
- 现象：套牌名任意位置含 `bot` 子串即打标。
- 建议：默认改为更明确的模式，或在文档强调需按本机情况收紧。

### L6. 废弃异常判定残留

- 位置：`is_abnormal` / `abnormal_reason` 贯穿 store、API、UI、CSV
- 现象：判定已废弃（恒 0），界面与导出仍保留整套字段。
- 建议：R10 统一清理或明确仅作兼容读，不再展示。

### L7. 依赖无版本上界

- 位置：`requirements.txt`（`fastapi>=0.110`、`uvicorn>=0.29`）
- 影响：未来大版本升级可能直接破坏运行。
- 建议：锁定经验证的下界+上界，或提供 lock/约束文件。

### L8. 本机 Python 小版本混用痕迹

- 现象：`__pycache__` 同时存在 3.12 与 3.13 编译产物。
- 建议：项目约定单一开发/运行版本（README 已写 3.11+，可补充推荐版本）。

### L9. 启动阶段失败几乎不可见

- 位置：`app/main.py`（`_boot_tasks` 内归档/回填/Bot 打标均为 `except Exception: pass`）
- 影响：失败后仅 `booting` 变回 false，用户无法区分「无数据」与「回填失败」。
- 建议：把失败类型与时间写入 `/api/status`。
