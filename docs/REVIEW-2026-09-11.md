# 全项目复查与 R11 修复清单（2026-09-11）

本文件记录 R1—R10.3 完成后的专项复查结果，作为下一轮修复和发布验收的依据。

本轮只做检查、复现和登记，没有修改业务代码，也没有把下列事项标记为已修复。上一份检查记录见 [REVIEW-2026-09-10.md](REVIEW-2026-09-10.md)，已在 R9—R10 中关闭或改变产品口径的问题不在本文重复列为待修复项。

## 结论

R1—R10.3 的主体功能已经可用，现有自动测试全部通过，当前约 1.1 万场资料下的查询速度也可以接受。但是，日志解析中仍有两条能够稳定复现的数据污染路径，修复并核对历史数据前不建议发布当前工作区。

此外，启动失败不可见、配置覆盖、页面请求串场和发布版本滞后会直接影响用户对统计结果的信任。它们应与解析修复一起进入下一轮，而不宜继续作为零散优化积压。

## 严重问题：会污染历史统计

### C1. 迟到的比赛结果会写入下一场对局

**位置**：`app/events.py::_on_final_result`

**现状**：解析器在读取结果载荷前，先把当前对局 `_cur` 选为写入目标；只有没有当前对局时才使用最近闭合的 `_last`。它没有使用 `finalMatchResult.matchId` 校验结果属于哪场比赛。

**稳定复现顺序**：

1. `m-old` 开始并收到 `MatchCompleted`；
2. `m-new` 开始，成为 `_cur`；
3. `m-old` 的 `finalMatchResult` 迟到；
4. 解析结果变成 `m-old` 无胜负，`m-new` 被错误写成 `m-old` 的胜负和结束原因。

合成复现得到：

```text
m-old  result=None  reason=None
m-new  result=win   reason=Concede
```

**真实日志证据**：抽查最近 8 个日志来源，共找到 12 个结果块；12 个 `finalMatchResult` 均带 `matchId`，同时包含整场和单局结果。因此可以按载荷中的比赛 ID 精确路由，不需要依赖“当前或上一场”的时间猜测。

**影响**：

- 胜率会被写到错误的对局；
- 错误胜负会与另一场的先后手、赛事、套牌和对手主将关联；
- 由这些字段生成的日报、套牌详情、主将交手和历史变化都会被连带污染；
- 仅依靠 `match_id` 幂等写入无法防止这种串场，因为错误数据本身使用的是新对局 ID。

**修复要求**：

- 先解析 `finalMatchResult.matchId`，再寻找相同 ID 的当前、最近闭合或待确认对局；
- 结果 ID 与目标对局不一致时禁止写入；
- 暂时找不到目标时进入有上限的待确认队列，并记录可见诊断；
- 去重键使用结果载荷的 `matchId`，不能继续使用预先选中的目标 ID。

**验收用例**：

- 当前对局正常收到自己的结果；
- `MatchCompleted` 后结果迟到，但下一场尚未开始；
- 下一场已开始后，上一场结果迟到；
- 两场结果以逆序到达；
- 没有 `matchId` 的旧格式保持保守兼容，但不得覆盖已明确属于另一场的记录。

### C2. BO3 第一局首回合结束时，第二局先后手丢失

**位置**：`app/events.py::_on_gre`

**现状**：局号推进依赖“上一局已经看到 `turnNumber > 1`，随后再次看到 `turnNumber == 1`”。若第一局在第一回合投降、断线或通过其他方式结束，解析器从未设置 `_saw_turn_gt1`，第二局的第一回合仍写入 `game_no=1`。

合成复现得到：

```text
game 1  play_draw=draw  result=loss
game 2  play_draw=None  result=win
```

第二局结果由 `resultList` 创建，但它的先后手已经错误落入第一局，所以最终形成字段错位。

**实际数据库核对**：当前有 1,301 场 BO3，其中 1,269 场存在第二局；发现 8 条后续局先后手缺失。它们目前都来自 Untapped 导入，不能证明本机实时日志已经触发此 bug，但解析算法本身已可稳定复现。

**影响**：

- BO3 逐局先后手不完整；
- 调度记录可能关联到错误局号；
- 用户查看“每一局先手还是后手”时会得到错误或未知结果。

**修复要求**：优先使用日志中的明确局号、游戏开始或游戏结束信号推进局号；只有旧日志缺少明确字段时才使用回合边沿，并为连续两个不同游戏状态的 `turnNumber=1` 提供可靠去重条件。

**验收用例**：

- 第一局正常打到第二回合后进入第二局；
- 第一局在第一回合结束后进入第二局；
- 重复收到同一局的第一回合状态，不得误增局号；
- BO3 打满三局，每局先后手、胜负和调度均对应正确局号。

## 高优先级：会造成静默漏数、配置丢失或页面显示错位

### H1. 启动归档和历史回填失败不可见

**位置**：`app/main.py::_boot_tasks`、`app/backfill.py::backfill`

启动任务在后台运行，归档、回填和 Bot 标记的异常均被直接忽略。无论是否成功，最终都会把 `booting` 改为 `false`。用户无法区分“确实没有历史数据”和“历史回填失败”。

回填使用独立 SQLite 连接，API 在服务启动后可以同时创建并使用主连接。WAL 和超时能缓解竞争，但无法保证长时间回填期间不发生写锁失败，而失败目前没有可见提示。

**修复要求**：

- 为归档、回填、Bot 标记分别保存开始时间、完成时间、处理数量和错误摘要；
- `/api/status` 显示当前阶段和失败状态；
- 回填与其他写操作统一经过单写者队列或同一把锁；
- 失败后提供明确重试入口，不把失败显示成正常完成。

### H2. 单条写入失败没有事务隔离

**位置**：`app/main.py::_watch_loop.flush`

当前实现已经避免一条“毒数据”永久堵住整个待写队列，但每条 `upsert_match` 只包了一层 `try/except`，没有 SAVEPOINT 或逐条回滚。如果一次 upsert 在写完主表、重写部分子表后才失败，后续统一 `commit()` 可能提交半条记录；也可能由最终提交失败触发整批回滚，与页面显示的“只丢弃一条”不一致。

**修复要求**：每场比赛和每条段位快照使用独立 SAVEPOINT；失败时回滚到该 SAVEPOINT，再继续下一条。丢弃计数应记录具体阶段和比赛 ID。

### H3. 损坏的配置文件可能被自动覆盖

**位置**：`app/config.py::load_config`、`app/main.py::_persist_player_id`

`config.json` 无法解析时，程序静默使用默认配置。之后只要自动探测到玩家 ID，`_persist_player_id` 会把读取失败后的数据视为空字典，并通过临时文件替换原配置。结果可能只剩一个 `my_player_id`，原来的日志路径、数据库路径和其他设置全部丢失。

身份探测本身按日志中 `reservedPlayers.userId` 的出现频次选最高者。大多数普通记录下这个办法有效，但频繁与同一玩家对战、混入其他账号日志或日志不完整时仍可能选错；当前会把这个推测立即永久保存。

**修复要求**：

- 配置读取失败时保留原文件，禁止自动覆盖；
- 将损坏文件备份为带时间戳的副本，并在页面显示错误；
- 自动识别结果先作为“待确认身份”，展示可核对信息；
- 只有格式正确的配置才能执行原子更新。

### H4. 部分页面接口仍会被旧请求覆盖

**位置**：`web/app.js::loadMulligans`、`loadCommanders`、`loadOpponentTypes`、`loadMatches`、`loadTargeting`

日报、总览和套牌详情已经有部分请求序号保护，但上述接口没有。快速切换赛制、赛事、BO 模式或套牌，或者切换时碰上 15 秒自动刷新，较早发出的慢请求可能最后返回，把新筛选的页面内容覆盖成旧范围。

**修复要求**：建立整页统一的筛选版本号或 AbortController。每次筛选变化递增版本，所有接口渲染前核对版本；过期响应只能丢弃，不能更新 DOM。

## 中优先级：覆盖、导出和本地运维问题

### M1. 构筑对手类型的适用赛事覆盖不足

**位置**：`app/stats.py::is_constructed_opponent_event`

当前通过少量英文字符串判断赛事是否属于非主将构筑。真实资料中的以下明确构筑活动会被判为“不适用”：

- `MWM_Historic_AllAccess`
- `MWM_Explorer_AllAccess`
- `MWM_HistoricArtisan`
- `MWM_Pauper`
- 部分 Standard、Timeless、Alchemy 周中活动
- 部分 Decathlon 构筑项目
- 名称不含现有标记的特殊构筑活动

这不是胜负统计错误，但会缩小对手类型分母，并让用户无法给本应适用的构筑对局添加标签。

**修复要求**：建立明确的赛事元数据表，至少保存原始 ID、中文名、赛制大类、是否主将赛制、是否轮抽／现开、是否允许对手类型标签。未知赛事保持保守状态，并提供本地纠正入口。

### M2. CSV 导出未防护表格公式

**位置**：`app/stats.py::export_rows`

对手名、套牌名、赛事 ID 等文本原样写入 CSV。以 `=`、`+`、`-` 或 `@` 开头的内容在 Excel 中可能被解释成公式。对手名属于外部输入，不能假定安全。

**修复要求**：所有文本单元格共用 CSV 安全函数；危险前缀前加单引号，并覆盖制表符、换行和前导空白绕过情况。

### M3. `stop.bat` 可能结束占用相似端口的其他程序

**位置**：`stop.bat`

`findstr :8765` 是子串匹配，也可能命中 `:18765`、`:87650` 等端口，然后强制结束相应 PID。

**修复要求**：精确读取本地监听端口 8765，并核对 PID；条件允许时再检查进程命令行是否属于本项目。

### M4. 空套牌标签会阻止后续正确名称回填

**位置**：`app/store.py::upsert_match`

`COALESCE(matches.my_deck_tag, excluded.my_deck_tag)` 把空字符串当作已有值。一旦某来源写入 `""`，后续日志或导入得到的正确套牌名无法覆盖。

当前数据库没有发现空字符串套牌标签，因此这是尚未触发的确定性缺陷。

**修复要求**：入库前把空白标签规范为 NULL，或在 SQL 中使用 `NULLIF`。

### M5. 监听和关闭生命周期不完整

**位置**：`app/main.py::_watch_loop`、`on_shutdown`，`app/watcher.py` 日志轮换逻辑

- 监听线程没有顶层异常兜底和最终状态更新，线程意外结束后页面仍可能显示“监听中”；
- 关闭时直接关闭数据库连接，没有通知监听线程退出并等待当前写入完成；
- 日志轮换时未闭合的多行记录没有先 flush，跨轮换的尾部 JSON 可能丢失。

**修复要求**：使用停止事件管理线程生命周期；线程入口使用顶层 `try/finally` 更新状态；关闭时先停止、等待，再关闭连接；轮换前统一 flush 记录组装器。

## 性能观察

当前约 1.1 万场资料下，抽样接口耗时如下：

| 接口 | 观察耗时 |
|---|---:|
| 总览 | 约 42—45 ms |
| 日报 | 约 262—316 ms |
| 近期观察 | 约 244—253 ms |
| 200 条对局明细 | 约 39—44 ms |
| 对手类型 | 约 21—27 ms |
| 套牌全部记录详情 | 约 79—91 ms |

当前性能可以接受。页面一次刷新会并行发出多个请求，但服务端通过全局数据库锁串行执行，整体刷新接近各接口耗时之和，并且每 15 秒重复一次。等资料量继续增长后，可优先缓存日报、近期观察和筛选选项；目前不应抢在数据正确性修复之前处理。

### R11.3 实现与验证（2026-09-11）

## R11.2 历史数据处理原则

不要直接在现有数据库上猜测哪些胜负属于错误对局。可靠流程是：

1. 修复解析器并锁定回归测试；
2. 只读备份现有数据库；
3. 从已归档日志和其他来源重建一份临时数据库；
4. 比较新旧库的比赛总数、日期分布、胜负、先后手、BO3 逐局、套牌和主将覆盖；
5. 单独列出发生变化的记录及变化来源；
6. 人工核对代表性差异后再决定是否替换正式库。

这样可以修正已经被 C1、C2 影响的数据，同时避免用二次推测覆盖仍然正确的个人历史。
